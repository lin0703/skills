# 大数据开发面试题库

本题库用于生成大数据开发技术面试题。使用时根据 JD、简历和候选人项目裁剪，不要全量机械输出。每个条目都可以改写成「主问题 + 三轮追问 + 参考答案/答题方向」。

## 使用规则

- 项目题优先：如果简历中出现实际项目，先围绕项目追问真实参与深度，再补组件基础题。
- 数仓项目必须先问项目事实盘点：数据模型、主题域数量、每日数据量、历史总量、源系统/源表/字段规模、各层表数量、DWS 表和字段构成、候选人直接负责范围。
- 项目事实盘点必须写在主问题标题或追问标题里，不能只写进参考答案、考察点或风险信号。
- 组件题要落到工程实践：每个概念题至少有一轮追问候选人如何在项目中使用、优化或排障。
- 答案方向不要替候选人编造经历。项目材料没写数据量、集群规模、延迟、SLA 时，答案方向写「应能补充真实规模和指标」。
- 对不同版本差异明显的组件，追问候选人实际使用版本和当时能力边界。
- 生成面试题时必须按大数据开发固定 12 类组织：业务理解与需求拆解、数仓建模与分层设计、指标体系与口径管理、OLAP引擎、ETL/ELT 与数据链路开发、SQL 能力与查询优化、Spark/Hive 离线计算、数据湖仓、Flink/实时计算、数据质量、Kafka/CDC/消息链路、数据治理与资产化。
- 题库章节提供候选题，最终 Markdown 输出时必须按固定 12 类顺序重排，不能沿用题库读取顺序随意输出。
- 调度、补数、重跑、SLA、失败重试、告警类问题归入「ETL/ELT 与数据链路开发」或「数据质量」，不要作为独立技术类别输出。
- StarRocks、Doris、ClickHouse、SelectDB、Trino/Presto、物化视图和分区分桶优化归入「OLAP引擎」；Hudi、Iceberg、Delta Lake、湖仓一体、对象存储和表格式归入「数据湖仓」，两类不能合并。

## 1. 业务理解与需求拆解

### Q1 业务过程、主题域和需求拆解

主问题：请结合简历中的核心项目，说明你如何从业务需求拆解出主题域、指标、维度、报表或数据产品？

追问链：
- 追问 1：你是先理解业务过程还是先看源表？如何识别核心业务事件和关键维度？
- 追问 2：业务方提出一个报表需求时，你如何确认统计口径、过滤条件、时间口径和数据延迟要求？
- 追问 3：如果两个部门对同一指标口径理解不一致，你如何推动对齐并降低后续返工风险？

参考答案/答题方向：
- 强答案应能从业务过程抽象主题域和业务事件，例如交易、支付、退款、履约、用户行为等，而不是只罗列表名。
- 应覆盖指标口径、维度粒度、数据时效、报表使用场景、下游用户、验收方式和口径风险。
- 风险信号：只会按产品给的 SQL 开发报表，讲不清业务过程、指标口径和数据产品目标。

### Q2 离线数仓端到端设计

主问题：如果让你从 0 到 1 设计一个电商交易主题数仓，你会如何拆解业务过程并设计端到端链路？

追问链：
- 追问 1：你会先建哪些事实表和维表？粒度是什么？
- 追问 2：如何设计日增量、历史回刷、质量校验和上下游依赖？
- 追问 3：如何支持高频看板、明细查询和临时分析三类不同需求？

参考答案/答题方向：
- 应从业务过程出发，例如下单、支付、退款、发货，设计订单事实、支付事实、退款事实和用户/商品/店铺/地区维。
- 链路包括采集、ODS、DWD、DIM、DWS、ADS、调度、质量、元数据和权限，其中调度证据归入 ETL/ELT。
- 不同查询需求可用明细层、汇总层、物化视图、OLAP 引擎和指标服务分层承接。

## 2. 数仓建模与分层设计

### Q1 项目规模、数据源和数仓模型事实盘点

主问题：请先把你简历中核心数仓项目的事实讲清楚：业务域是什么，采用什么数仓数据模型，有多少个主题域，每日数据量和历史总量大概是多少，接入了多少个源系统、源表和核心字段？

追问链：
- 追问 1：你们为什么采用这种模型，是维度模型、范式模型、星型/雪花、宽表、Data Vault 还是混合模型？为什么不用其它模型？
- 追问 2：源系统和源表如何进入 ODS？哪些是全量、增量或 CDC？核心源表字段大概多少，字段变更如何影响下游模型？
- 追问 3：这些数据量下，核心任务耗时、SLA、分区策略、存储格式和历史保留周期是怎么定的？如果数据量增长 10 倍，模型和链路哪里会先出问题？

参考答案/答题方向：
- 强答案应能给出可验证的项目量级：主题域数量、源系统数量、源表数量、核心源表字段数量、日增记录数/存储量、历史总量、任务耗时和 SLA；材料未体现时要求候选人现场补充。
- 模型选择应能解释业务过程、查询场景、指标复用、维度一致性、开发成本和性能取舍；不能只说「公司规范」或「大家都这么做」。
- 风险信号：说不清数据模型、主题域、日增量、源表数量、字段规模和核心任务耗时，通常说明只做过局部 SQL 或报表维护，数仓建模能力不得评为「熟练」以上。

### Q2 DWS 层、核心表和字段设计细节

主问题：请展开说明你负责的 DWS 层设计：DWS 层一共有多少张表，覆盖哪些主题，每张核心表的粒度是什么，大概多少字段、多少指标、多少维度？

追问链：
- 追问 1：请选一张你最熟的 DWS 表，说明它的主键、分区键、统计周期、业务粒度、事实来源、维度来源、核心指标和下游 ADS 使用场景。
- 追问 2：DWS 层和 ADS 层的职责边界是什么？哪些指标沉淀在 DWS，哪些只放在 ADS？为什么这样拆？
- 追问 3：如果 DWS 表字段越来越多、多个主题混在一张宽表里、不同 ADS 重复计算同一指标，会产生什么问题？你如何拆表、复用指标或治理口径？

参考答案/答题方向：
- 强答案应能讲清 DWS 的复用目标、表数量、字段规模、主题覆盖、统计粒度、公共维度、指标来源和下游消费关系。
- DWS 不应只是「中间结果表」；应能解释它如何沉淀可复用汇总、降低 ADS 重复开发、保证口径一致、支撑不同报表和数据产品。
- 风险信号：只会说 DWS 是汇总层，但说不出具体表、字段、粒度、指标、维度和下游使用方；或把 ADS 报表 SQL 当作 DWS 设计。

### Q3 数仓分层和主题建模

主问题：请结合简历中的核心数据仓库项目，说明你如何设计 ODS、DWD、DIM、DWS、ADS 各层，以及主题域是如何划分的？

追问链：
- 追问 1：各层的职责边界是什么？哪些层保留明细，哪些层服务复用，哪些层直接服务报表或应用？
- 追问 2：事实表和维表的粒度如何确定？如何避免指标口径重复和跨主题复用困难？
- 追问 3：如果数据量增长 10 倍或新增实时链路，你会如何调整分区、汇总、调度和存储策略？

参考答案/答题方向：
- 强答案能先讲业务过程和指标口径，再讲分层职责，而不是只背层名。
- ODS 贴源保留原始或轻清洗数据；DWD 统一明细事实、清洗和标准化；DIM 管理公共维度和缓慢变化；DWS 按主题沉淀可复用汇总；ADS 面向具体应用和报表。
- 粒度要围绕业务事件确定，例如订单行、支付单、用户日行为；维表要讲主键、自然键、代理键、SCD、有效期和一致性维度。
- 扩容场景应覆盖分区裁剪、增量计算、冷热分层、预聚合、资源隔离、质量校验和下游 SLA。

## 3. 指标体系与口径管理

### Q1 指标体系和口径治理

主问题：你在项目里如何管理指标口径，如何保证同一个指标在不同报表中一致？

追问链：
- 追问 1：指标是写在 ADS SQL 里，还是沉淀到公共汇总层或指标平台？为什么？
- 追问 2：当业务方修改指标口径时，你如何评估影响范围并回刷历史数据？
- 追问 3：如何发现两个团队对同一指标口径理解不一致？如何用元数据或血缘降低沟通成本？

参考答案/答题方向：
- 强答案应覆盖指标定义、维度约束、统计周期、过滤条件、生命周期、负责人、版本变更和血缘。
- 公共指标应沉淀在 DWS/指标服务层，ADS 尽量只做场景适配，避免每张报表重复实现。
- 口径变更要有影响分析、历史回刷策略、灰度验证、双跑比对、审批记录和公告机制。
- 风险信号：只说「和产品确认」但没有口径文档、复用层、变更流程和数据校验。

## 5. ETL/ELT 与数据链路开发

### Q1 数据量、分区和增量策略

主问题：请说明项目的日增量、历史总量、核心表分区方式和增量计算策略。

追问链：
- 追问 1：为什么选择这个分区字段？有没有二级分桶、排序键或文件大小治理？
- 追问 2：迟到数据、重跑和补数如何处理？如何保证幂等？
- 追问 3：如果上游重复推送、乱序或回撤，明细层和汇总层如何保证最终一致？

参考答案/答题方向：
- 强答案应能给出真实量级、峰值、任务耗时和瓶颈，而不是只说「数据量比较大」。
- 分区通常按业务日期或事件日期；要结合查询条件、写入方式、回刷范围和小文件治理。
- 增量策略应覆盖水位、分区覆盖、merge/upsert、去重键、幂等写入和失败重试。
- 迟到和回撤要说明窗口范围、历史重算、拉链或状态修正机制。

### Q2 补数、重跑和幂等

主问题：离线链路任务失败、上游补历史或业务要求重算时，你如何设计补数、重跑和幂等机制？

追问链：
- 追问 1：补数前如何确认业务日期、数据区间、依赖范围和下游影响？
- 追问 2：任务重跑时如何避免重复写入或覆盖错误分区？
- 追问 3：如果上游补历史导致下游多个链路都要重算，你如何编排并控制资源和 SLA？

参考答案/答题方向：
- 强答案应覆盖业务日期、数据区间、上下游依赖、临时表加原子替换、分区覆盖、唯一键 merge、写入 label、任务锁、成功标记和回滚方案。
- 复杂补数需要批次管理、依赖拓扑、资源隔离、质量校验和结果对账。
- 风险信号：只说「清掉任务重跑」但没有幂等、依赖影响分析、校验和回滚方案。

### Q3 调度依赖和链路稳定性

主问题：你如何设计离线批处理链路的上下游依赖、失败重试、SLA 和告警？

追问链：
- 追问 1：跨任务、跨系统或跨 DAG 的数据依赖如何表达？如何判断数据真正就绪？
- 追问 2：失败重试、超时、优先级、资源隔离和补数窗口如何设计？
- 追问 3：大量任务或动态任务导致调度变慢、链路雪崩时，你如何优化？

参考答案/答题方向：
- 应能说明依赖拓扑、数据就绪语义、任务参数化、重试策略、超时、SLA、告警、队列/资源池和任务日志。
- 使用 Airflow、DolphinScheduler、Azkaban 或自研平台都可以，但不能把工具名等同于链路治理能力。
- 风险信号：只会配置 DAG 依赖，讲不清数据依赖、失败恢复、补数编排和 SLA 影响。

## 10. 数据质量

### Q1 数据质量监控

主问题：你参与过哪些数据质量监控？规则如何配置，告警如何闭环？

追问链：
- 追问 1：质量规则是硬编码在 SQL 里，还是平台化配置？规则覆盖哪些类型？
- 追问 2：质量告警如何区分阻断、告警和观察？误报和漏报如何处理？
- 追问 3：发生核心指标异常时，你如何定位是源端、传输、计算、调度还是消费端问题？

参考答案/答题方向：
- 常见规则包括空值、唯一性、枚举值、范围、波动、环比/同比、主外键一致性、账实核对、分区完整性和延迟。
- 强答案应有规则配置、调度执行、阈值、责任人、告警渠道、工单、恢复动作和复盘。
- 阻断规则适合核心链路的强一致校验；波动规则要结合业务日历和节假日，避免简单固定阈值。
- 定位应从血缘、任务日志、分区产出、上游数据到下游消费逐层排查。

### Q2 数据质量事故复盘

主问题：线上核心报表数据异常，你如何排查、修复并复盘？

追问链：
- 追问 1：你如何快速判断影响范围和是否需要停止下游消费？
- 追问 2：如何定位根因并修复历史错误数据？
- 追问 3：复盘后你会增加哪些机制避免再次发生？

参考答案/答题方向：
- 快速止血包括确认异常指标、影响报表/用户、异常分区、最近变更、上游产出和下游缓存。
- 根因定位沿血缘逐层查源端、采集、清洗、计算、调度、权限和展示。
- 修复要有回滚/重算、校验、公告和复盘；长期机制包括变更审批、自动化质量规则、灰度、血缘影响分析和 SLA 告警。

## 12. 数据治理与资产化

### Q1 元数据、血缘和数据治理

主问题：你是否参与元数据维护、血缘建设或数据治理？具体做了哪些工作？

追问链：
- 追问 1：元数据包括哪些内容？技术元数据、业务元数据和管理元数据如何关联？
- 追问 2：血缘是如何采集的？SQL 解析、调度依赖和运行时日志分别能解决什么问题？
- 追问 3：如果要下线一张表，如何评估影响并推动治理闭环？

参考答案/答题方向：
- 技术元数据包括库表字段、分区、存储、任务、血缘；业务元数据包括指标、口径、主题域、标签；管理元数据包括负责人、生命周期、等级和权限。
- 血缘来源可包括 SQL 解析、调度 DAG、数据集注册、运行日志和手工补充；不同来源准确度和成本不同。
- 表下线要看访问热度、下游血缘、任务依赖、权限、负责人确认、灰度停用和回滚窗口。
- 风险信号：只维护表注释，没有治理流程、血缘、生命周期和责任归属。

## 7. Spark/Hive 离线计算

### Q1 Hive 表设计、分区分桶和文件治理

主问题：Hive 离线表设计时，你如何选择分区、分桶、存储格式和压缩方式？

追问链：
- 追问 1：业务日期、事件日期、更新时间分别作为分区字段会带来什么差异？
- 追问 2：小文件、分区过多或分桶不合理会如何影响 Spark/Hive 查询和调度？
- 追问 3：如果核心明细表既要支持日常增量又要支持历史回刷，你如何设计表结构和写入策略？

参考答案/答题方向：
- 强答案应结合查询过滤条件、写入方式、回刷范围、数据生命周期和成本选择分区字段。
- 存储格式和压缩应说明 ORC/Parquet、列裁剪、谓词下推、压缩比、读写性能和兼容性。
- 风险信号：只按日期建分区，讲不清小文件、分桶、文件格式和下游查询模式。

### Q2 Shuffle、宽窄依赖与 Stage 划分

主问题：简述 Spark 的宽窄依赖，以及 Spark 如何划分 Stage；每个 Stage 的 Task 个数由什么决定？

追问链：
- 追问 1：哪些算子通常会触发 Shuffle？为什么 Shuffle 是性能瓶颈？
- 追问 2：Stage 边界如何产生？失败重试时宽依赖和窄依赖对恢复有什么影响？
- 追问 3：如果一个 Stage 的 Task 特别少或特别多，会造成什么问题？你如何调整？

参考答案/答题方向：
- 窄依赖指子 RDD 分区依赖父 RDD 的少量固定分区，通常可流水线执行；宽依赖指子分区依赖多个父分区，通常需要 Shuffle。
- groupByKey、reduceByKey、join、distinct、repartition、sortByKey 等常见操作会触发 Shuffle。
- Spark 以 ShuffleDependency 为边界切分 Stage；一个 Stage 内的窄依赖可合并流水线执行。
- Task 个数通常由该 Stage 最后一个 RDD 的分区数决定。Shuffle 后 reduce 端 Task 数由 shuffle 分区数决定，例如 `spark.sql.shuffle.partitions` 或 RDD partitioner。
- 调优方向包括合理设置分区数、避免小文件和过度并行、使用 AQE、合并小分区、处理热点 key。

### Q3 数据倾斜

主问题：Spark 数据倾斜如何识别和处理？

追问链：
- 追问 1：你如何判断是数据倾斜、资源不足、GC 问题还是外部存储慢？
- 追问 2：Join 倾斜和聚合倾斜分别怎么处理？
- 追问 3：AQE 能解决哪些倾斜场景？哪些场景仍需要业务侧改造？

参考答案/答题方向：
- 识别方式包括 Spark UI 中 Task 耗时/输入数据量极不均、少数 task 长尾、shuffle read/write 异常、executor GC 或 spill 指标异常。
- Join 倾斜可用广播小表、热点 key 拆分加盐、两阶段聚合、预过滤、分桶、AQE skew join。
- 聚合倾斜可用 map-side combine、局部聚合再全局聚合、key 加盐、拆分热点业务。
- 不能只说「加资源」；强答案要能定位热点 key 和解释改造副作用。

### Q4 persist、cache 和 checkpoint

主问题：Spark 的 persist 和 cache 有什么区别？什么时候需要 checkpoint？

### Q5 map 和 flatMap

主问题：Spark 的 map 和 flatMap 有什么区别？举一个业务例子。

### Q6 reduceByKey 和 groupByKey

主问题：Spark 的 reduceByKey 和 groupByKey 性能差异是什么？

追问链：
- 追问 1：为什么 reduceByKey 通常比 groupByKey 更适合聚合？
- 追问 2：groupByKey 什么时候仍然合理？
- 追问 3：如果 key 倾斜，reduceByKey 是否一定能解决？为什么？

参考答案/答题方向：
- reduceByKey 会在 map 端进行预聚合，减少网络传输和 reduce 端内存压力。
- groupByKey 会把同一 key 的全部 value 拉到一起，容易产生大量 shuffle 和 OOM。
- groupByKey 在确实需要某个 key 下的全量明细集合时才合理，但要控制数据量。
- key 倾斜时 reduceByKey 只能降低数据量，不能消除热点 key 的单点聚合压力。

## 9. Flink/实时计算

### Q1 Exactly-Once 和 Checkpoint

主问题：Flink 如何保证 Exactly-Once？Checkpoint 机制是什么？

追问链：
- 追问 1：Checkpoint barrier 如何在算子间传播？对齐和非对齐 checkpoint 有什么差异？
- 追问 2：端到端 Exactly-Once 为什么还依赖 Source 和 Sink？
- 追问 3：Flink + Kafka + 外部存储如何设计一致性？如果 Sink 不支持事务怎么办？

参考答案/答题方向：
- Flink 通过分布式快照保存算子状态和输入位置，失败后从 checkpoint 恢复状态并从记录位置重放。
- Exactly-Once 不是只靠 Flink 内部；Source 要可重放，Sink 要支持幂等、事务、两阶段提交或可回滚写入。
- Kafka Source offsets 会随 checkpoint 管理；事务型 Kafka Sink 或两阶段提交 Sink 可实现端到端一致性。
- 如果 Sink 不支持事务，需要幂等主键、去重表、临时表加原子提交或业务补偿。

### Q2 Flink 反压

主问题：Flink 如何处理反压？你如何定位反压来源？

追问链：
- 追问 1：反压会如何影响吞吐、延迟和 Checkpoint？
- 追问 2：如何区分 Source 太快、算子计算慢、状态访问慢、Sink 写入慢？
- 追问 3：你会用哪些手段缓解反压？哪些手段只是掩盖问题？

参考答案/答题方向：
- 反压是下游处理能力不足导致上游发送受阻，表现为吞吐下降、延迟上升、checkpoint barrier 传播变慢。
- 定位看 Flink UI backpressure、busy/idle/backpressured time、算子并行度、watermark 延迟、checkpoint duration、外部系统写入指标。
- 缓解手段包括提升瓶颈算子并行度、优化计算和序列化、异步 IO、批量写、状态优化、扩容外部存储、限流 source。
- 只盲目加并行度可能导致外部系统压力更大或状态重分布成本上升。

### Q3 状态与 State Backend

主问题：Flink 中 keyed state 和 operator state 有什么区别？State Backend 如何选择？

追问链：
- 追问 1：为什么 keyed state 需要 keyBy？key group 和并行度有什么关系？

- 追问 3：状态 schema 变更或作业升级时如何保证兼容？

参考答案/答题方向：
- keyed state 绑定到 keyBy 后的 key，常用于按用户、订单、设备维护状态；operator state 绑定到算子实例，常用于 source 分片等。
- RocksDB/ForSt 等磁盘型后端适合大状态，内存型后端低延迟但容量受限；具体取决于版本和部署。
- 优化方向包括增量 checkpoint、合理 TTL、状态拆分、减少状态大小、异步快照、调整 checkpoint 间隔和超时。
- 升级要考虑 savepoint、序列化器兼容、状态名称稳定和回滚策略。

### Q4 Watermark 与乱序

主问题：Flink Watermark 解决什么问题？如何处理乱序和迟到数据？

追问链：
- 追问 1：事件时间、处理时间和摄入时间有什么区别？
- 追问 2：Watermark 延迟设置过大或过小分别有什么影响？
- 追问 3：窗口关闭后的迟到数据如何处理？如何修正下游结果？

参考答案/答题方向：
- Watermark 表示事件时间进度，用于触发基于事件时间的窗口计算。

- 迟到处理可用 allowed lateness、side output、补偿流、更新型 Sink 或离线校正。

### Q5 Flink SQL 与 DataStream 选择

主问题：实时任务中什么时候用 Flink SQL，什么时候用 DataStream API？

## 11. Kafka/CDC/消息链路

### Q1 Topic、Partition、Consumer Group 和 Offset

主问题：Kafka 的 Topic、Partition、Consumer Group 和 Offset 分别是什么？它们如何影响并行度和消费语义？

追问链：
- 追问 1：为什么同一个 consumer group 内一个 partition 同一时刻只能由一个 consumer 消费？
- 追问 2：增加 partition 数会带来哪些收益和风险？
- 追问 3：offset 自动提交和手动提交有什么差异？失败时可能出现什么语义？

参考答案/答题方向：
- Topic 是逻辑主题，Partition 是并行和有序日志单元，Consumer Group 实现组内负载均衡，Offset 表示消费位置。
- 分区内有序，不保证跨分区全局有序；并行度上限通常受 partition 数限制。
- 增加 partition 可提升并行度和吞吐，但可能改变 key 到 partition 的映射，影响顺序、存储和协调开销。
- 自动提交简单但可能丢失或重复；手动提交可控制处理完成后提交，但仍要处理重试和幂等。

### Q2 Kafka 顺序性

主问题：Kafka 如何保证消息顺序？什么情况下顺序会被破坏？

追问链：
- 追问 1：如果要求同一个订单的事件有序，你如何设计 key 和 partition？
- 追问 2：Producer 重试、幂等和 max.in.flight 会影响顺序吗？
- 追问 3：下游多线程消费如何既保证吞吐又保证同 key 有序？

参考答案/答题方向：
- Kafka 只保证同一 topic-partition 内的消息顺序。
- 同业务实体使用相同 key 可路由到同一 partition；跨 partition 不保证全局顺序。
- Producer 配置、重试和非幂等发送可能影响顺序；现代配置要结合幂等和 in-flight 限制理解。
- 下游多线程可按 key 分发到固定 worker，或单 partition 串行处理关键路径。

### Q3 积压与延迟

主问题：Kafka 消费积压如何定位和处理？

追问链：
- 追问 1：如何判断瓶颈在 producer、broker、consumer 还是下游存储？
- 追问 2：增加 consumer 实例为什么不一定有效？
- 追问 3：如果积压已经持续数小时，你如何恢复 SLA 并避免数据丢失？

参考答案/答题方向：
- 观察 consumer lag、消费速率、broker 网络/磁盘、rebalance、fetch/commit 指标、下游写入耗时。
- consumer 并行度受 partition 数限制；下游慢时盲目增加 consumer 只会扩大压力。
- 处理方式包括临时扩容、提高并行度、优化批量和反序列化、限流上游、跳过非核心历史、分级恢复和补偿校验。

### Q4 Kafka Exactly-Once 与事务

主问题：Kafka 的幂等 Producer 和事务分别解决什么问题？

追问链：
- 追问 1：At-most-once、At-least-once、Exactly-once 在消费处理链路中如何体现？
- 追问 2：Kafka 事务如何把生产消息和消费 offset 原子提交？
- 追问 3：如果下游是数据库或 StarRocks，如何实现端到端不重不丢？

参考答案/答题方向：
- 幂等 Producer 解决 producer 重试导致的单分区重复写；事务把多分区写入和 offset 提交纳入原子边界。
- At-most-once 可能丢，At-least-once 可能重，Exactly-once 要求重放和提交边界一致。
- 外部数据库通常依赖幂等主键、事务写、去重表、版本号或两阶段提交；不能只声称 Kafka 本身保证全链路 Exactly-Once。

### Q5 CDC/binlog 同步链路

主问题：你如何设计 MySQL binlog 到 Kafka/Flink/数仓的 CDC 同步链路？

- 追问 2：DDL 变更、主键更新、删除事件和乱序到达如何处理？
- 追问 3：如果端到端延迟突然升高，你如何定位是源库、CDC 组件、Kafka、Flink 还是下游存储问题？

参考答案/答题方向：
- 强答案应覆盖 Canal/Flink CDC/Debezium 等工具的快照、位点、checkpoint、反序列化、schema 变更和 Exactly-once 边界。
- 应能说明 topic 设计、partition key、offset/位点管理、幂等落地、延迟监控、积压处理和源端压力控制。
- 风险信号：只知道「监听 binlog」但讲不清全量增量衔接、位点恢复、DDL 和下游一致性。

- External Catalog 让 StarRocks 访问外部元数据和数据文件，减少搬迁数据的成本。
- 性能优化要覆盖文件格式、分区裁剪、列裁剪、统计信息、物化视图、缓存和热点数据内表化。
- 一致性取决于外部表格式、元数据刷新和物化视图刷新策略；需要明确延迟和容错边界。

## 6. SQL 能力与查询优化

### Q1 窗口函数

主问题：窗口函数和 group by 的区别是什么？常见窗口函数有哪些？

追问链：
- 追问 1：如何实现每个用户最近一次登录记录？
- 追问 2：row_number、rank、dense_rank 有什么区别？
- 追问 3：窗口函数数据量很大时有哪些性能风险？

参考答案/答题方向：
- group by 会聚合成每组一行；窗口函数保留明细行并在窗口内计算。
- 最近一条可用 `row_number() over(partition by user_id order by login_time desc)=1`。
- 性能风险包括大分区排序、数据倾斜、内存溢出和缺少分区裁剪。

### Q2 拉链表和缓慢变化维

主问题：什么是拉链表？它和 SCD Type 2 有什么关系？

追问链：
- 追问 1：如何设计有效开始日期、结束日期和当前标识？
- 追问 2：如何处理同一天多次变更、乱序到达和删除状态？
- 追问 3：查询某个历史时点维度状态时 SQL 如何写？

参考答案/答题方向：
- 拉链表记录实体属性随时间变化的历史版本，常用 start_date、end_date、is_current 表达有效区间。
- 需要稳定业务主键、变更比对、版本关闭、新版本插入和幂等重跑。
- 历史查询用业务时间落在有效区间内，注意闭开区间设计和时区。

### Q3 Join 和去重

主问题：大表 Join 和数据去重常见风险是什么？你如何优化？

追问链：
- 追问 1：Join 前后数据量异常膨胀通常是什么原因？
- 追问 2：维表一对多或脏数据导致重复时如何治理？
- 追问 3：如何在 SQL 层、模型层和质量层共同防止重复指标？

参考答案/答题方向：
- 膨胀原因包括 join key 不唯一、维表多版本未限定、过滤条件缺失、粒度不一致和笛卡尔积。
- 优化包括预聚合、去重、限定有效期、选择正确 join 类型、广播小表、分区裁剪和 key 标准化。
- 质量层应增加唯一性、主外键、行数波动和指标稽核。
