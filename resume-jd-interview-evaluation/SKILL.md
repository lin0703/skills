# 大数据开发面试评价

## 核心原则

- 技术能力评估仅基于面试评价长文本或沟通记录中的实际回答，不参考简历技能清单、简历项目技术栈或 JD 技术要求给分。
- 简历只用于提取基本信息、工作经历、年限、到岗、薪资、稳定性等客观背景；JD 只用于判断岗位方向和技术类别范围。
- 输出正文使用专业面试记录风格，直接陈述事实和判断；避免“候选人表示”“候选人具备”“该候选人”“JD要求”“岗位匹配”等模板化表述。
- 面试没有问到或没有答出对应技术项时，不从简历补证据；对应能力写成“面试未体现可验证回答”。
- 面试官重点追问的问题是核心评判依据，答不上来必须体现在对应类别评级和总结不足中。
- 结论直接写评判结果，不引用面试原文，不写转述式表达。
- 按面试对话和 JD 判断岗位方向并选择技术类别；不要把 Java 微服务标准套到大数据或运维岗位上。
- 技术评价只描述面试对话中明确出现的信息和可由答题质量直接支撑的判断，不补写学习能力、抗压能力、沟通积极性等无证据套话。
- 技术评价关注“能力域 + 答题质量 + 关键缺口”，不要把面试中出现的函数名、组件名、API 名、参数名或底层技术点堆成知识点清单。

## 输入材料处理

- 用户提供目录时，优先读取 `沟通记录.txt`、`面试评价.txt`、`面评.txt`、JD 文档、简历 PDF/docx/txt。
- PDF 简历或 JD 可使用 `scripts/extract_pdf_text.py` 提取文本。
- JD 只作为方向识别材料；除非用户明确要求，不在输出中单独写 JD 要求、JD 差距或岗位匹配结论。
- 简历内容不得用于技术能力评级；可用于 `基本信息`、`工作经历`、`其它` 中的非技术客观信息。
- 输出默认写入当前工作区的 `outputs\面试评价\` 文件夹；目录不存在时先创建。生成本地文件时必须使用 `.txt` 扩展名，文件名使用 `姓名_年限_大数据开发面试评价.txt`，除非用户明确指定其它格式或路径；若用户只粘贴材料且未要求落盘，则直接在回复中输出结构化评价。
- 需要详细模板时读取 `references/evaluation-template.md`。

## 定位等级

等级判定基于岗位方向和面试回答质量，不按工作年限定级。

| 等级 | 通用标准 |
| --- | --- |
| 初级初 | 只能完成入门编码、脚本或 SQL，岗位核心基础薄弱，关键概念不清楚 |
| 初级中 | 可在指导下完成简单模块、单表或单链路开发，会使用常见工具但原理和排障较弱 |
| 初级高 | 能独立完成常规业务模块、ETL 任务、报表或运维任务，掌握核心工具基本用法 |
| 中级初 | 能独立承担子系统、主题域或完整数据链路，理解核心原理、数据流和常见问题 |
| 中级中 | 能做方案设计、性能优化、规范沉淀，可独立搭建或改造服务框架、数仓链路或运维体系 |
| 中级高 | 有复杂项目主导或带人经验，能处理架构、稳定性、性能、治理类问题 |
| 高级 | 具备专业领域架构设计和落地经验，能主导完整技术体系、平台化方案或数据体系建设 |

## 技术能力评判标准

等级判定基于面试回答质量，不按工作年限定级。

| 等级 | 标准 |
| --- | --- |
| 精通 | 深入理解原理和源码，能讲清设计思想和取舍，有生产环境调优经验 |
| 熟练 | 能准确描述原理、使用场景、注意事项，能回答追问，有实际项目经验 |
| 一般 | 知道怎么用，但原理不清楚，被追问后回答模糊，仅简单使用过 |
| 较差 | 概念混淆、仅听说过、回答错误或关键问题答不上来 |
| 无经验 | 未接触过或完全不了解 |

降级规则：

- 面试官重点提问的问题回答较差，该项最高评为“较差”。
- 多个核心技术问题答不上来，整体定位下调。
- 工作年限长但回答质量低，按实际能力定级，不按年限。
- 回答“不清楚”“没接触过”“学过但没用过”，评为“较差”或“无经验”。
- 面试官连续追问 1-2 个基础问题均答不上来，该项评为“较差”。
- 简历技能清单不参与评级；若面试对简历项目进行了追问，以追问回答质量作为评级依据。
- 技术能力评估只能使用“精通、熟练、一般、较差、无经验”五类等级，不使用其他评级词。

## 技术评价颗粒度

- 技术能力评价不是技术知识点盘点。每条评价采用“【类别】- 等级，概括做过的能力域 + 面试追问暴露出的答题质量/关键缺口”。
- 优先使用能力域概括，例如“Hive 行列转换”“JSON 字段处理”“消息链路治理”“数据资产治理”“湖仓表格式能力”；不要逐项罗列函数名、组件名、API 名、参数名或底层机制名。
- 具体技术名只在以下场景保留：该技术名是类别核心方向，如 Doris、Spark/Hive、Flink、Kafka；面试官明确追问该点且回答质量直接影响评级，如 Checkpoint 与 Savepoint 区别答不上来；该细节是判断“熟练、一般、较差”的关键证据，不写会导致评级依据不清。
- 单条评价中连续并列的具体函数、组件或机制名不宜超过 2 个；如出现 3 个以上并列技术名，优先抽象为能力域，除非这些点均被面试官逐项追问且直接影响评级。
- 如果只是说明使用过某类能力，改成概括表达。例如写“能说明 Hive 行列转换、JSON 字段处理、集合聚合等常见场景”，不要写成“能说出 lateral view、explode、json 解析、collect_list/collect_set”。
- 工作经历不要写成技术栈清单。优先写实际开发过程和职责能力域，例如“能说明离线数仓分层开发、指标加工、数据服务、实时告警、数据质量校验、字段规范和血缘追踪等工作的实际开发过程”。
- 数据治理、湖仓、消息链路等类别尤其避免知识点堆砌。写体系化能力和回答深度，例如“对数据资产使用情况、生命周期、成本与安全治理等体系化治理能力回答不足”。
- 湖仓能力不要罗列一堆产品或机制名，除非面试中逐项追问。可写“未体现主流湖仓表格式、读写模式、对象存储建湖或湖仓架构设计经验”。
- Kafka/CDC 类评价不要写成机制列表。可写“对消息一致性、消费位点、积压处理、CDC 同步和端到端延迟治理缺少系统化说明”；如果面试没有明确追问某个机制，不要主动扩展成详细机制清单。
- 总结和定位也使用能力域表达，不堆砌技术栈。可写“实时一致性原理、离线计算调优、OLAP 慢查询定位、消息链路和湖仓一体能力不足”。

## 技术类别选择

先按面试实际考察维度归类，再按岗位方向补齐应评价的技术域。能合并则合并，但大数据开发岗位的数仓能力必须拆细。用户提供 JD 时，可用来识别岗位方向，但输出中不要写“JD要求”“岗位要求”“岗位匹配”。技术类别的评级依据只能来自面试回答。

### Java 方向

1. Java 基础 - Java8 特性、集合、JVM、多线程、并发工具
2. Spring Boot - 配置加载、Bean 生命周期、自定义 starter、AOP、事务
3. Spring Cloud/微服务 - 注册发现、网关、OpenFeign、限流熔断、分布式事务、分布式锁
4. 中间件 - Redis、MQ、ES、流程引擎、缓存一致性
5. 数据库 - MySQL、索引、事务、SQL 调优、分库分表
6. 问题排查 - OOM、线程阻塞、系统假死、慢接口、日志链路
7. 设计能力 - 高并发系统设计、大数据量系统设计、接口和领域建模
8. 业务能力 - 能完整描述业务核心流程、边界条件和数据闭环

### 大数据开发方向

大数据开发岗位固定使用以下 12 类，并按以下重要程度顺序逐项输出评价。每类都必须输出一条“【类别】- 等级，评价内容”，不得省略、合并或新增其它大数据开发类别；面试未考察或未答出有效内容时，输出“无经验”或“较差”并说明面试未体现可验证回答。以下类别说明用于判定能力边界，不代表输出时逐项列举所有技术名。

1. 业务理解与需求拆解 - 能从业务过程抽象主题域、指标、维度、报表和数据产品，识别口径风险
2. 数仓建模与分层设计 - ODS/DWD/DWS/ADS 分层、主题域、事实表/维度表、粒度、宽表、星型/雪花模型、缓慢变化维、公共维度
3. 指标体系与口径管理 - 原子指标、派生指标、复合指标、统计口径、口径一致性、指标复用、指标血缘、报表口径对齐
4. OLAP引擎 - Doris、StarRocks、ClickHouse、SelectDB、Trino/Presto、物化视图、分区分桶、查询性能优化
5. ETL/ELT 与数据链路开发 - 全量/增量、拉链表、幂等、补数、重跑、上下游依赖、数据落地、离线批处理链路
6. SQL 能力与查询优化 - 复杂 SQL、窗口函数、多表关联、分区裁剪、执行计划、Join 策略、数据倾斜、小文件、存储格式
7. Spark/Hive 离线计算 - Spark SQL/Core、Shuffle、资源配置、任务调优、Hive 表设计、分区分桶、UDF/UDAF
8. 数据湖仓 - Hudi、Iceberg、Delta Lake、湖仓一体、表格式、Compaction、Merge-on-read/Copy-on-write、对象存储
9. Flink/实时计算 - Flink SQL/DataStream、Watermark、状态管理、Checkpoint、Exactly-once、窗口、迟到数据、实时维表关联
10. 数据质量 - 完整性、唯一性、准确性、及时性、波动监控、空值/重复校验、源目标对账、异常定位和修复
11. Kafka/CDC/消息链路 - Kafka topic/partition/consumer group、offset、积压处理、Canal/Flink CDC、binlog 同步、端到端延迟
12. 数据治理与资产化 - 元数据、血缘、权限、脱敏、生命周期、成本治理、规范沉淀、数据资产目录

数仓开发能力拆分要求：

- 面试对话或 JD 体现数仓、离线数仓、实时数仓、指标平台、BI、报表、数据治理方向时，必须完整输出上述 12 类；具体评级仍只看面试回答。
- 调度、补数、重跑、SLA、失败重试、告警等证据归入“ETL/ELT 与数据链路开发”或“数据质量”，不要新增“调度与任务治理”类别。
- 若面试材料涉及性能瓶颈、慢 SQL、倾斜、资源调优，单列“SQL 能力与查询优化”或对应计算引擎。
- 若面试对话或 JD 同时涉及数据湖仓和 OLAP引擎，必须拆成“数据湖仓”和“OLAP引擎”两项，不合并为一类；具体评级仍只看面试回答。
- 若只会写 SQL 或报表，但讲不清分层、粒度、事实维度、指标口径，数仓建模与指标体系不得评为“熟练”以上。
- 若能讲清主题域拆分、公共维度、指标复用、增量策略、质量校验和补数方案，可体现为数仓开发优势。

### 系统运维方向

1. Linux 系统 - 安装、配置、加固、调优、故障排查
2. 虚拟化/云平台 - VMware、OpenStack、私有云/公有云
3. 容器/K8s - Docker、Kubernetes、容器编排
4. 监控体系 - Zabbix、Prometheus、Grafana、告警
5. 数据库运维 - MySQL/Oracle、主从、备份恢复、SQL 调优
6. 中间件 - Redis、MQ、Nginx、ELK
7. CI/CD - Jenkins、GitLab CI、ArgoCD
8. 网络/安全 - 网络配置、等保合规、防火墙、负载均衡

二、工作经历：
1. 公司名称（起止年月，X年）：工作内容总结描述

## 输出要求

1. 工作经历从简历提取，按时间倒序，最多 3 条；不要写成技术栈清单，技术细节只写面试中实际追问或回答到且影响评价的内容。
2. 技术能力评估每项一行，格式为“【类别】- 等级，评价内容”，评价内容按“能力域 + 答题质量 + 关键缺口”组织，等级只能使用“精通、熟练、一般、较差、无经验”。
3. 大数据开发岗位优先输出细分后的数仓能力，不使用“数据库 - 大数据熟练”这类粗分类。
4. 用户长文本已有明确判断时，保留其核心观点并结构化改写，不为了显得客观而削弱原判断。
5. 生成本地文件时使用纯文本文件格式（`.txt`），不要使用 Markdown 标题符号、代码围栏、表格或多余 Markdown 装饰，除非用户明确要求其它格式。
6. 默认输出路径为当前工作区的 `outputs\面试评价\姓名_年限_大数据开发面试评价.txt`；写文件前确保 `outputs\面试评价\` 已存在。
7. 第一行固定使用 `姓名_年限_大数据开发面试评价`，例如 `张三_5年_大数据开发面试评价`；年限从简历或面试材料提取，优先使用阿拉伯数字加“年”，无法确认年限时使用 `未知年限`。
8. 分节标题固定使用中文序号和中文冒号：`一、基本信息：`、`二、工作经历：`、`三、技术能力评估：`、`四、其它：`、`五、总结：`、`六、定位：`。
9. 排版规则：文档标题后空一行；每个分节标题前保留一行空行；分节标题后立即接正文，不再额外空行；正文条目之间不空行。
10. 基本信息、工作经历、其它、总结中的正文条目保留 `1.`、`2.` 这类阿拉伯数字序号；技术能力评估按类别每项一行，不额外添加数字序号，除非用户明确要求。
11. 定位等级必须与回答质量匹配，不能虚高。
12. 评价内容优先使用无主语事实句，例如“面试中能说明 ODS/DWD 清洗和 ADS 报表开发流程”；不要写“候选人xxx”。
13. 不输出“JD要求”“岗位要求”“与JD匹配”“岗位匹配风险”等措辞；需要说明风险时，写成“面试未考察...”或“面试未体现可验证回答...”。
14. 避免 AI 化套话和空泛形容；每条技术评价至少包含一个面试答题表现、追问结果或明确缺口。
15. 避免把技术能力评估、总结和定位写成“掌握 A、B、C，了解 D、E，不会 F、G”的清单；优先写成招聘面试记录式判断，例如“能说明离线链路开发流程，但对增量、幂等、补数重跑和链路治理方案回答不足”。
