# 大数据开发面试评价模板

输出必须使用中文，保持专业招聘面试记录风格。生成本地文件时默认使用纯文本 `.txt` 格式，并写入当前工作区的 `outputs\面试评价\` 文件夹；目录不存在时先创建。除非用户要求，不要输出 Markdown 标题、代码围栏或表格。

写作以事实陈述为主，避免 AI 化模板语气。正文不要写“候选人表示”“候选人具备”“该候选人”“JD要求”“岗位匹配”等表述；JD 仅用于识别岗位方向和技术类别，不在输出中单独评价。技术能力评估仅基于面试对话中的实际回答，不参考简历技能清单。技术评价关注“能力域 + 答题质量 + 关键缺口”，不要把面试中出现的函数名、组件名、API 名、参数名或底层技术点堆成知识点清单。

如果技术能力分类需要用户确认，先输出：

```text
技术能力类型建议：
1. [类型A]：[为什么从原始面评或沟通记录中归纳出该类型]
2. [类型B]：[为什么从原始面评或沟通记录中归纳出该类型]
以下为初版结构化评价：
```

```text
姓名_年限_大数据开发面试评价

一、基本信息：
1. [姓名、性别、年龄、婚育、所在地、求职意向等，仅写材料明确出现的信息]

三、技术能力评估：
【[技术类型1]】- [精通/熟练/一般/较差/无经验]，[概括做过的能力域 + 面试追问暴露出的答题质量/关键缺口]
【[技术类型2]】- [精通/熟练/一般/较差/无经验]，[概括做过的能力域 + 面试追问暴露出的答题质量/关键缺口]
【[业务能力]】- [精通/熟练/一般/较差/无经验]，[说明业务流程理解、复杂度、抽象能力、项目 ownership 的事实依据]

四、其它：
1. [稳定性、到岗时间、空窗、地域、薪资、团队角色等客观补充]
2. [面试中提到的项目规模、稳定性指标、职责边界，或面试未考察到的关键能力项]

五、总结：
1. 优势：[基于面试回答中的项目事实概括 2-4 个优势]
2. 不足：[概括面试回答暴露的关键缺口、技术深度不足、项目复杂度不足或未体现可验证回答的能力项]

六、定位：
[级别]，[建议推进/谨慎推进/不建议推进]
```

## 写作口径

- 第一行固定使用 `姓名_年限_大数据开发面试评价`，例如 `张三_5年_大数据开发面试评价`；年限从简历或面试材料提取，优先使用阿拉伯数字加“年”，无法确认年限时使用 `未知年限`；姓名、城市、岗位或业务方向写入 `基本信息`，不要再使用 `[姓名]（[岗位]）` 作为标题。
- 默认输出路径固定为当前工作区的 `outputs\面试评价\姓名_年限_大数据开发面试评价.txt`；写文件前确保 `outputs\面试评价\` 已存在，除非用户明确指定其它路径。
- 分节标题固定使用中文序号和中文冒号：`一、基本信息：`、`二、工作经历：`、`三、技术能力评估：`、`四、其它：`、`五、总结：`、`六、定位：`。
- 排版规则：文档标题后空一行；每个分节标题前保留一行空行；分节标题后立即接正文，不再额外空行；正文条目之间不空行。
- `基本信息`、`工作经历`、`其它`、`总结` 的正文条目保留 `1.`、`2.` 这类阿拉伯数字序号；`技术能力评估` 按类别每项一行，不额外添加数字序号，除非用户明确要求。
- `基本信息` 通常写 2-4 条；不要为了凑数补充未出现信息。
- `工作经历` 按最近到较早排序，简历只用于提取公司、时间、职责等经历事实；不要写成技术栈清单，技术细节只写面试中实际追问或回答到且影响评价的内容。
- `技术能力评估` 每类一行，格式固定为 `【技术类型】- 等级，评价内容`；评价内容按“能力域 + 答题质量 + 关键缺口”组织，等级只能使用 `精通、熟练、一般、较差、无经验`。
- 技术类型必须从用户长文本和沟通记录中动态归纳，不要直接沿用示例里的技术栈；JD 只用于判断岗位方向，不作为正文表述对象。
- 技术能力评级只能基于面试对话中的实际回答；简历技能清单、简历项目技术栈、JD 技术要求都不能作为评级依据。
- 用户长文本已有明确判断时，要保留其核心观点并改写为结构化表达；不要为了显得客观而削弱用户原判断。
- `其它` 用于记录非核心但影响推进的信息，例如到岗、稳定性、空窗、薪资、面试中提到的项目规模和职责边界。
- `总结` 只写优势和不足两条，避免重复工作经历细节。
- `定位` 必须给出明确推进建议，不要含糊。
- 评价句式优先使用无主语事实句，例如“面试中能说明 ODS/DWD 清洗和 ADS 报表开发流程”；不要使用“候选人xxx”的主语模板。
- 技术评价必须包含事实依据、答题表现或明确缺口；不要写“有一定经验”“学习能力较强”“综合素质较好”等无证据套话。
- 技术风险或不足写成“面试未考察...”或“面试未体现可验证回答...”，不要使用泛泛的材料缺失、JD 要求或岗位匹配类表述。
- 技术能力评价不是技术知识点盘点。优先使用能力域概括，例如“Hive 行列转换”“JSON 字段处理”“消息链路治理”“数据资产治理”“湖仓表格式能力”；不要逐项罗列函数名、组件名、API 名、参数名或底层机制名。
- 具体技术名只在以下场景保留：该技术名是类别核心方向，如 Doris、Spark/Hive、Flink、Kafka；面试官明确追问该点且回答质量直接影响评级，如 Checkpoint 与 Savepoint 区别答不上来；该细节是判断“熟练、一般、较差”的关键证据，不写会导致评级依据不清。
- 单条评价中连续并列的具体函数、组件或机制名不宜超过 2 个；如出现 3 个以上并列技术名，优先抽象为能力域，除非这些点均被面试官逐项追问且直接影响评级。
- 数据治理、湖仓、消息链路等类别尤其避免知识点堆砌；用体系化能力和回答深度表达，例如“对数据资产使用情况、生命周期、成本与安全治理等体系化治理能力回答不足”。
- 总结和定位也使用能力域表达，不写成技术栈堆砌；例如写“实时一致性原理、离线计算调优、OLAP 慢查询定位、消息链路和湖仓一体能力不足”。

## 大数据开发方向技术类型

大数据开发岗位固定输出以下 12 类。按以下重要程度顺序逐项输出评价，不要省略、合并或新增其它类别；面试未考察或未答出有效内容时，也要输出“无经验”或“较差”并说明面试未体现可验证回答。以下列表用于判定能力边界，不代表输出时逐项列举所有技术名。

- 业务理解与需求拆解：从业务过程抽象主题域、指标、维度、报表和数据产品，识别口径风险。
- 数仓建模与分层设计：ODS/DWD/DWS/ADS 分层、主题域、事实表/维度表、粒度、宽表、星型/雪花模型、缓慢变化维、公共维度。
- 指标体系与口径管理：原子指标、派生指标、复合指标、统计口径、口径一致性、指标复用、指标血缘、报表口径对齐。
- OLAP引擎：Doris、StarRocks、ClickHouse、SelectDB、Trino/Presto、物化视图、分区分桶、查询性能优化。
- ETL/ELT 与数据链路开发：全量/增量、拉链表、幂等、补数、重跑、上下游依赖、数据落地、离线批处理链路。
- SQL 能力与查询优化：复杂 SQL、窗口函数、多表关联、分区裁剪、执行计划、Join 策略、数据倾斜、小文件、存储格式。
- Spark/Hive 离线计算：Spark SQL/Core、Shuffle、资源配置、任务调优、Hive 表设计、分区分桶、UDF/UDAF。
- 数据湖仓：Hudi、Iceberg、Delta Lake、湖仓一体、表格式、Compaction、Merge-on-read/Copy-on-write、对象存储。
- Flink/实时计算：Flink SQL/DataStream、Watermark、状态管理、Checkpoint、Exactly-once、窗口、迟到数据、实时维表关联。
- 数据质量：完整性、唯一性、准确性、及时性、波动监控、空值/重复校验、源目标对账、异常定位和修复。
- Kafka/CDC/消息链路：Kafka topic/partition/consumer group、offset、积压处理、Canal/Flink CDC、binlog 同步、端到端延迟。
- 数据治理与资产化：元数据、血缘、权限、脱敏、生命周期、成本治理、规范沉淀、数据资产目录。

数仓能力拆分规则：

- 大数据数仓类岗位方向必须完整输出上述 12 类评价；每类评级只看面试回答。
- 调度、补数、重跑、SLA、失败重试、告警等证据归入“ETL/ELT 与数据链路开发”或“数据质量”，不要新增“调度与任务治理”类别。
- 面试材料出现慢 SQL、倾斜、资源调优、执行计划时，单列“SQL 能力与查询优化”或对应计算引擎。
- 面试对话或 JD 同时涉及数据湖仓和 OLAP引擎时，必须拆成“数据湖仓”和“OLAP引擎”两项，不合并为一类；具体评级仍只看面试回答。
- 只会写 SQL 或报表，但讲不清分层、粒度、事实维度、指标口径时，“数仓建模与分层设计”和“指标体系与口径管理”不得评为“熟练”以上。
- 能讲清主题域拆分、公共维度、指标复用、增量策略、质量校验和补数方案时，在优势中突出数仓开发能力。

## 风险点

如果面试对话不足，可在 `其它` 中补充 1-3 个客观风险；后续流程默认没有技术面，因此只写面试中暴露的事实缺口，不写技术追问建议。

- 面试未考察到岗位方向的关键技术项。
- 面试中项目规模、性能指标、稳定性指标、团队职责边界描述不清。
- 面试中只提到组件/框架名称，缺少原理、调优、排障或落地细节。
- 面试回答暴露的业务域经验与目标方向差异较大，迁移能力缺少可验证回答。
- 大数据岗位若面试未体现主题域建模、事实维度表设计、指标口径治理、增量同步、任务调度、数据质量、慢 SQL 或数据倾斜处理证据，需要在客观风险中说明。
